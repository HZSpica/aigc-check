# aigc_check.py 使用文档

**版本**：v1.1.0　|　**依据**：GB 45438-2025、TC260-PG-20252A / 20257A / 20258A / 20259A / 202510A / 202511A / 202512A

---

## 1. 这是什么

一个**离线**的文件元数据检测器，用来回答三个问题：

1. 这个文件里有没有中国标准（GB 45438-2025）要求的 AIGC 隐式标识？
2. 如果有，标识是否合规？是谁生成的？
3. 如果没有，有没有国际通行的 C2PA 溯源清单作为旁证？

---

## 3. 安装

把 `aigc_check.py` 这一个文件复制到任意目录即可，无需安装。

建议连同 `selftest.py` 和 `samples/` 一起放，方便随时验证工具本身是否正常：

```
aigc-check/
├── aigc_check.py      主程序
├── 
```

### 装完先自检

```bash
cd aigc-check
python selftest.py
```

正常输出结尾：

```
合计 19 例，通过 19，失败 0
```

只要不是 19/19，就说明文件在传输中被改动或 Python 环境异常，先别用它出结论。这一步在换机器、换 U 盘后务必重跑。

## 4. 五分钟上手

```bash
# 1) 查一张图
python aigc_check.py 111.png

# 2) 查一个文件夹（只看第一层文件）
python aigc_check.py ../test

# 3) 查文件夹及所有子目录，只出汇总表
python aigc_check.py ../test -r --summary

# 4) 结果存成文件（给案件卷宗/领导看）
python aigc_check.py ../test -o 检测结果.txt
```

对应四种输出形态：

| 目的 | 命令 |
|---|---|
| 看单个文件的完整证据 | `python aigc_check.py 文件` |
| 快速过一批（一屏看完） | `python aigc_check.py 目录 -r --summary` |
| 出正式报告（存档） | `python aigc_check.py 目录 -o 报告.txt` |
| 交给别的系统处理 | `python aigc_check.py 文件 --json` |

## 5. 参数说明

```
python aigc_check.py <路径...> [选项]
```

| 参数 | 说明 |
|---|---|
| `路径...` | 可给多个文件、目录，或混合。目录默认**只取第一层文件** |
| `-r`, `--recursive` | 递归子目录 |
| `--summary` | 只输出汇总表，不输出详细报告 |
| `--json` | 输出机器可读 JSON（符合 TC260-PG-202512A 7.5 f 要求）。**优先级高于 `--summary`** |
| `--dump` | 报告末尾附容器/元数据结构（段、chunk、box 树），用于排查"标识是不是被剥了" |
| `-o 文件`, `--output 文件` | 报告写入指定文件，屏幕只提示"报告已写入 xxx" |
| `-v`, `--version` | 显示版本 |
| `-h`, `--help` | 显示帮助 |

### 注意事项

- **路径带空格或中文，必须加引号**：`python aigc_check.py "D:\案件 2026\证据 01.png"`
- Windows 下推荐在 **PowerShell 或 CMD** 里运行；Git Bash 也可，但路径要写成 `/c/...` 形式
- `-o` 指定的文件若已存在会**直接覆盖**，出报告前留意
- 目录扫描时，非媒体文件（如 `.txt`、`.exe`）也会被读一遍做关键字扫描，不报错，但没必要，建议先筛出目标格式

## 6. 报告怎么读

以一张真实的字节系 AI 图片为例（节选自 `测试结果_4张图片.txt`）：

```
==========================================================================
文件: 111.png
路径: C:\...\test\111.png
格式: PNG 图片    大小: 3,387,998 字节
==========================================================================

一、中国标准标识（GB 45438-2025）：[检出] 检出标准位置的文件元数据隐式标识
  1) [标准位置] XMP 元素 TC260AIGC
     位置: chunk iTXt(XMP) @0x21
     原文: {"Label":"1","ContentProducer":"00119144030008867405X210001",...}
二、标识内容解析
  Label              = 1
  ContentProducer    = 00119144030008867405X210001
  ContentProducer 解码 → 格式码00 | 组织 | 绑定统一社会信用代码 | 主体9144030008867405X2 | 服务生成合成服务
三、合规校验（GB 45438-2025 附录 E）
  [✓] 七要素齐全（附录 E）
  [✗] 传播方要素已填写（附录 E 注 1）  —— ContentPropagator 与 PropagateID 均为空
四、其他溯源体系：C2PA 内容凭证（非 GB 45438，仅作旁证）
  检出：PNG 私有 chunk caBX @0x21，合计 23,654 字节
  生成工具: OpenAI Media Service API
  数字源类型: trainedAlgorithmicMedia（训练算法生成媒体（IPTC 定义：AI 生成））
五、结论
  检出合规的文件元数据隐式标识。
  该文件按标识应认定为：属于人工智能生成合成内容。
```

### 各段看什么

> 段落是**按需出现**的：没有安全防护信息就没有第三段，没有 C2PA 就没有第四段。下面的编号以完整报告为例，实际看标题即可。

| 段落 | 作用 | 关键点 |
|---|---|---|
| 一、中国标准标识 | 有没有、在哪、原文长什么样 | `[标准位置]` 才是硬证据；`[非标准/线索]` 只能当参考 |
| 二、标识内容解析 | 七个字段的实际值 | `Label` 的 1/2/3 含义不同，见下节；编码能反查主体 |
| 三、安全防护信息 | 有没有签名/杂凑 | 有 `SecurityData` 说明带防护，可信度更高 |
| 四、合规校验 | 逐项 ✓/✗ | 有 ✗ 就是"标了但不合规"，要指出具体项 |
| 五、C2PA 凭证 | 国际体系的旁证 | 只有"未检出"时才出现，不要套用 GB 45438 结论 |
| 六、结论 | 一句话定性 + 下一步 | 直接引用时要连同限定条件一起引用 |

### 位置字段怎么读

| 写法 | 含义 |
|---|---|
| `chunk iTXt(XMP) @0x21` | PNG 里 XMP 文本块，文件偏移 0x21（33 字节处） |
| `APP1/XMP @0xE2` | JPEG 的 APP1 段 |
| `moov.udta.meta.ilst` | MP4/MOV 的元数据清单 |
| `ID3v2 TXXX 帧（desc=AIGC）` | MP3 标签帧 |
| `docProps/custom.xml` | Office 文档的压缩包内路径 |

`@0x...` 是十六进制偏移，取证时可用于在十六进制编辑器里定位、截屏固定证据。

## 7. 判定结果与合规项

### 7.1 三种判定

| 判定 | 屏幕显示 | 含义 | 怎么用 |
|---|---|---|---|
| `found` | 检出 | 标准位置有 AIGC 标识 | 可认定"文件声明为 AI 生成"，再看合规项 |
| `informal` | 疑似 | 有 AIGC 相关内容但不在标准位置 | 只能作线索，需人工核验，不能直接下结论 |
| `not_found` | 未检出 | 无任何标准标识 | **不能**推论"非 AI 生成"，按结论里的建议继续查 |

汇总表里 `Label` 列显示 `-` 有两种情况：真的没有标识，或标识存在但字段残缺。后者在详细报告里会给出具体缺失项。

### 7.2 合规校验项含义

| 校验项 | 依据 | 什么情况会 ✗ |
|---|---|---|
| 标识字段可解析 | — | JSON 结构损坏、被截断 |
| 七要素齐全 | 附录 E | 缺字段，或 `Label`/`ContentProducer`/`ProduceID` 为空 |
| Label 取值合法 | 附录 E c) | 不是 `1`/`2`/`3` |
| ContentProducer / ContentPropagator 为 27 位编码 | 20252A | 值为 27 位但结构不符（前 4 位不是 `0011`/`0021` 这类合法组合） |
| ContentProducer / ContentPropagator 要素取值方式 | 附录 E d) | 只在值为**名称**时出现，恒为 ✓，并标注"以名称存储，溯源能力弱" |
| 传播方要素已填写 | 附录 E 注 1 | `ContentPropagator`/`PropagateID` 为空或只填一半 |
| 字符集符合附录 E j) | 附录 E j) | 值里含中文、控制字符等非 ASCII 可打印字符 |

**最容易误判的两项**，单独说清：

1. **用名称不算违规。** 附录 E 允许"名称或编码"，`ContentProducer:"doubao"` 是合规的。它的问题只是无法反查主体，报告会标注"溯源能力弱"。真正要挑的是编码写错、传播方漏填。
2. **`Label=1` 与 `2`/`3` 证明力不同。** `1` 是生成方主动声明"这是我生成的"；`2`（可能）/`3`（疑似）是平台推断。写结论时不能一律说成"AI 生成"。


*本工具与文档仅用于合规检测与取证辅助，不构成法律意见。*
